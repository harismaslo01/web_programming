rules for submitting and defending the project. Please read it carefully at the start of the semester.


Introduction
Students will individually develop a fully functional, responsive and deployed single-page web
application with a REST backend implemented using the FlightPHP framework and a MySQL
database. The application must include at least 5 database entities with CRUD operations,
role-based access, an integration with at least one external API, middleware with info and error
logging, and it must be documented in a README file.

The project is worth 15% of the final grade and consists of 5 milestones. The frontend must be
fully connected with the backend by the beginning of Week 12, when Milestones 1 – 4 are
defended.

AI tools are allowed in the project, provided that their use is documented as described in this
document and that you understand and can explain every part of your code.

Project Requirements
 1.​ The project has to be a web application implemented using the PHP, JS and MySQL
    technology stack. Libraries like Bootstrap, Highcharts, DataTables and similar are very
    desirable in the project.
 2.​ Mixing backend and frontend code is not allowed. The REST backend should be pure PHP
    code, while the frontend should be just HTML, CSS and JS.
 3.​ Usage of the FlightPHP framework for the REST API is a must.
 4.​ Usage of PHP PDO is required for accessing the database layer.
 5.​ The project API must be documented using OpenAPI documentation.
 6.​ The application must have AJAX requests implemented.
 7.​ Every student has to create a GitHub repository where they implement their project. The
    GitHub repository is used to monitor students' activity and progress of work.
 8.​ The application has to be mobile friendly.
 9.​ The application must be a single page application.
 10.​The project should have at least 5 different entities (e.g., Users, Products, Orders,
    Categories, Reviews) with basic CRUD operations implemented.
 11.​JWT (JSON Web Tokens) is a must for authentication and authorization.
 12.​The project should be hosted and publicly available through a domain. The GitHub Student
    Developer Pack (https://education.github.com/pack) can be used for this purpose; any other
    hosting providers are allowed and desirable.
 13.​The application must support at least 2 different roles.
 14.​Usage of HTML templates is recommended. Bootstrap-based templates are also
    recommended.
 15.​Fully connected frontend and backend. Every entity must be manageable through the user
    interface via AJAX calls to your REST API, with no static or hard-coded data left in the
    frontend.
 16.​External API. The application must integrate at least one external (third-party) API.
 17.​Additional middleware. Besides JWT verification, the backend must have additional
    middleware (see below).
 18.​Logging. The backend must write an info log and an error log (see below).
 19.​Configuration and secrets. Database credentials, the JWT secret and API keys are stored in
    a configuration file that is not committed to GitHub; a template file (e.g., config.example.php)
    is committed instead.
 20.​AI usage documentation. The repository must contain AGENTS.md and docs/AI_LOG.md
    (see below).

Detailed Requirements
External API
  ●​ At least one call to a third-party API.
  ●​ The data must be used in a meaningful feature that is visible in the user interface, not only
     printed as raw JSON.
  ●​ Failures must be handled: set a timeout, handle error responses, write the failure to the
     error log and return a user-friendly message. The application must keep working if the
     external API is unavailable.
  ●​ Examples: weather (OpenWeatherMap), currency rates (Frankfurter), countries (REST
     Countries), maps (OpenStreetMap Nominatim), books (Open Library), recipes (TheMealDB),
     email sending (Mailtrap), or any other API relevant to your project.

Middleware
Middleware must be reusable code registered in FlightPHP, not code copied into every route.
Required:

  ●​ Authentication: verifies the JWT token on all protected routes and returns 401 if it is
     missing, invalid or expired.
  ●​ Authorization: a reusable role check that returns 403 if the user does not have the required
     role.
  ●​ Request logging: writes every request to the info log.
  ●​ Error handling: catches unhandled exceptions, writes them to the error log and returns a
     JSON error message without exposing stack traces, SQL queries or file paths.

Logging
  ●​ Info log (backend/logs/info.log): every request (time, method, route, status, user and role),
     successful logins and registrations, and external API calls.
  ●​ Error log (backend/logs/error.log): unhandled exceptions, database errors, failed logins,
     rejected requests (401/403), and external API failures.
  ●​ Log can be a database table.

 TIP Example log lines: [2026-12-01 14:05:12] INFO GET /orders 200 user=12 role=admin 35ms and

 [2026-12-01 14:05:13] ERROR POST /orders 500 user=12 PDOException: ... (OrderDao.php:42).
 During the defense you will be asked to show your logs and explain an entry.

AI usage documentation
You may use any AI tool. The goal is not to measure how much AI you use, but whether you use it in
a controlled, professional way. Both files must be updated in every milestone:

  ●​ AGENTS.md (repository root): a context file for AI coding assistants, written by you: project
      description, technology stack, architecture rules, folder structure, naming conventions and
      rules that the AI must follow.
  ●​ docs/AI_LOG.md: one section per milestone with the AI tools you used and for which parts,
      the most important prompts, and at least 2 cases where the AI was wrong or produced poor
      code: what was wrong, how you noticed it and how you fixed it.
  ●​ If you do not use AI tools, state this in AI_LOG.md; AGENTS.md is still required, since it
      documents your architecture.

 CAUTION A missing or not updated AGENTS.md or AI_LOG.md results in −0.25 points for that milestone.

README
The README must contain: project description, entities and their relationships, roles and test
accounts for each role, the external API and the feature it supports, instructions for running the
project locally (importing the .sql file and creating the configuration file), the link to the Swagger
documentation, and the link to the deployed application.

Project Defense
Milestones 1 – 4 are defended in Weeks 12. The schedule will be published on the LMS. Only
milestones submitted on time with correct pull requests and correct reviews are eligible for
defense.

Conditions for the defense:

  ●​ The milestone was submitted on time with a correct pull request and reviewer.
  ●​ The frontend is fully connected with the backend. This is checked at the beginning of the
      defense; if the application is not fully connected, the defense ends and Milestones 1 – 4 are
      graded with 0.
  ●​ The application runs during the defense.
Defense format (without AI tools):

  ●​ Demo: run the application and show the main features, including the external API feature.
  ●​ Request trace: for an action chosen by the examiner, explain the complete path: click →
      AJAX call → route → middleware → service → DAO → SQL → response → UI update, and
      show the related log entries.
  ●​ Code questions: explain a file or function chosen by the examiner.
  ●​ Live change: implement a small change in your code, such as adding a field or restricting an
      endpoint to admins.

 CAUTION The points earned for each milestone are multiplied by your level of understanding shown at

 the defense: 100% (full), 50% (partial) or 0% (cannot explain the code). Code that you cannot explain is
 not worth points.

How to Submit a Milestone?
 1.​ Each milestone should be implemented on a separate branch (milestone1, milestone2,
     milestone3, milestone4, milestone5).
 2.​ All milestone related code should be added to the milestone branch.
 3.​ Before the deadline, a PR must be created and user ibu-web-programming2001 must be
     added as reviewer (and as collaborator on the repository).
 4.​ Late submissions will not be accepted, and a given milestone will be graded with 0. If you do
     not add a collaborator on time, you will not be able to add a collaborator as a reviewer.
     Collaboration requests submitted during the weekend before the deadline will not be
     accepted.
 5.​ Once the PR is approved, the reviewer will merge the code to the main branch, and you can
     create a branch for the next milestone and continue with your work.

 CAUTION Do not merge the milestone branch into the main branch. Doing so will prevent the reviewer

 from verifying your submission.
